## 3. 播放性能（重点）

### 3.1 硬解路径与起播链（已验证）

原始日志 `docs/evidence/tv-play-chain.txt`：

- **视频硬解确定**：`dumpsys media.player` 亦列出 `OMX.MS.AVC.Decoder` 带 `hw-accelerated: 1`、支持 Baseline/Main/High@5.1。
- **起播 496 ms**：`35.658 → 36.154`。
- 期间的 `BadPortIndex` / `nBufferCountActual failed: -22` 是 MTK OMX 的回退路径警告，最终 `Now Executing` 成功，**不是播放错误**。

### 3.2 音频为何是软解（已验证，原因标注为推断）

- 观察事实：`OMX.google.aac.decoder` 被实例化（`audio/mp4a-latm`，48 kHz）；播放期间音频输出正常。
- 观察事实：`/vendor/etc/media_codecs.xml:563` 中 `OMX.MS.AAC.Decoder` 的声明是
  `<MediaCodec name="OMX.MS.AAC.Decoder" type="audio/mp4a-latm-hw">`，即**私有 mime**；
  `dumpsys media.player` 里它挂在 `Media type 'audio/mp4a-latm-hw'` 下。
- 推断（未做强制指定实验）：Media3 按标准 `audio/mp4a-latm` 查询 MediaCodecList，匹配不到私有 mime 组件，故落到 Google 软解。
- **本轮不改**：1x/2x 的 CPU 与音画表现均可接受，强行指定私有 mime 解码器兼容性未验证。
  记为可优化项，不做无证据的"优化"。

### 3.5 无效测量的自纠记录（方法论，全部作废重测）

用户要求实验依据精确，以下 4 次误测均**主动推翻、不作结论**：

1. **误判"长时间静置导致会话过期"**：第一次 `SMB 未连接` 发生在 App 启动 13 分钟后，我推测是静置过期；
   但第二次距冷启动仅 4 分钟且一直在播放，同样在 seek 后约 3.02 s 报错 → 推翻，改判为
   "**片尾静置后 SMB 连接变为不可用**"，与静置绝对时长无关。
2. **误按 OK 把视频暂停**：`KeyRouter.kt` 与原型 `pEnter()` 都规定全屏态 OK = `pToggle()`。
   我两次在测量开始按 OK，导致 `gfxinfo Total frames=0`、截图 MD5 相同 —— 那是**暂停态**，不是"零掉帧"。
   按 OK 恢复后三张截图 MD5 全不同，确认 App 行为与原型一致。
3. **测量窗口内视频播到片尾**：命令往返耗时使 3:25 的片子播完，静止的片尾 LOGO 造成
   "Janky 4.76% / 音轨 0 active / CPU 下降" 的假象。改为"先快退到片头、立即测量"后重取。
4. **三次 LEFT 只移了焦点**：`KeyRouter` 规定焦点在 `pmenu:*` 时 LEFT/RIGHT 只移焦点、不触发快退
   （条件是 `!focusTag.startsWith("pmenu")`）。正确序列是 **UP 回 `ptrack` 再 LEFT**。

## 7. 本轮发现并修复的 2 个缺陷

### 7.1 播放页倍速档位串了设置页数据源（已验证缺陷 → 已修代码，电视回归待办）

- **原型事实**：`merged-shelf-list.html` 有两套档位 ——
  播放页菜单 `data-spd = 0.5/0.75/1/1.5/2/3`（1122–1129 行），
  设置页 `SPEEDS = [0.75,1,1.25,1.5,2]`（2701 行）；`pPickSpeed()` 直接取 `data-spd`，**不用 SPEEDS**。
- **代码缺陷**：`Nav.kt:452` / `KeyRouter.kt:130` 用 `presetSpeeds`（设置页）去取播放页菜单的值，
  `AppState.openSpeedMenu()` 也用它定位焦点 → `psi:6` 越界 `getOrElse{1f}` 回落到 1.0x。
- **电视复现**：菜单焦点在 `3.0x`（`docs/tv-114-3x-focus.png`）→ 应用后按钮显示 **`1.0x`**（`tv-115-3x-applied.png`）。
- **修法**：新增 `playMenuSpeeds = [0.5,0.75,1,1.5,2,3]` 作为播放页菜单**唯一数据源**；
  `presetSpeeds` 保留给设置页；`openSpeedMenu()` 按原型 fallback 到 `psi:3`(1.0x)；
  `PlayerPage` 当前档高亮改引用同一常量。改动文件：`AppState.kt`、`Nav.kt`、`KeyRouter.kt`、`PlayerPage.kt`。

### 7.2 片尾静置后 seek 报「SMB 未连接」且静默定格（已验证缺陷 → 已修代码，电视回归待办）

- **三次稳定复现**（全部是"播到片尾静止 → 再 seek"，报错都在 seek 后约 3.0 s）：
  `15:07:22.861`、`15:13:23.899`、`15:24:14.062`，
  堆栈均为 `IOException: SMB 未连接：请先在数据源页连接共享` @ `SmbDataSource.open()`。
- **对照实验**：干净重启后**片中** seek 完全正常（`15:13:18.264 flush → 15:13:18.311` 新首帧，PTS 变化，4 s 零错误），
  说明 seek 本身无问题。FLV 无索引，Media3 每次 seek 都要重新 `open` 数据源，旧实现直接抛错。
- **静默失败**：`onPlayerError()` 对该消息只走 `else -> toast(...)`，toast 一闪即逝，
  画面定格而用户看不到任何提示（`tv-34-after-error.png` 无任何错误层）。
- **未下断言的部分**：连接为何变 false（Windows 会话超时 / 电视网络省电 / smbj 心跳缺失）没有抓包或服务端日志，
  只确认 `share?.isConnected` 变 false 且 App 没有探测/重连机制。
- **修法**：
  1. `SmbSession.ensureConnected()`：用上次成功配置透明重连，退避 1 s / 2 s 递增、连续失败 3 次即停
     （禁止狂重连），`resetReconnectBackoff()` 供手动重试清零；
  2. `SmbDataSource.open()`：连接失效时先 `ensureConnected()`，仍失败才抛带原因的 `IOException`；
  3. `onPlayerError()`：SMB 断开类错误改弹**可见诊断层**（复用 `openSmbDiag`），
     标题「读不出视频：共享连接已断开」，按钮「重新连接并继续播放」，回调在 IO 线程强制重连。

## 8. 安装通道结论（本轮新增证据，已验证）

`adb install` 被封是上一轮结论。本轮补测了**不同通道**：

```
adb push <tv2.apk> /data/local/tmp/purecourse-tv2.apk   # 成功，12485350 B
adb shell pm install -r /data/local/tmp/purecourse-tv2.apk
→ Failure [INSTALL_FAILED_VERIFICATION_FAILURE]
```

`dumpsys package` 前后仍是 `versionCode=1 / versionName=1.0.0-p0`，未发生覆盖。

> 结论：TCL 封的是 **PackageManager 侧整个 ADB/shell 安装通道的验证环节**，
> 不只是 `adb install` 命令；换 `pm install` 本地包同样不通。
> 因此 tv2 只能 **U 盘 → 电视系统安装器**，或按用户计划**连手机用 ADB 安装验证**。

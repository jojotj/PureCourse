# 06 · 分辨率适配（1080P / 4K 电视显示完全一致）

## 1. 结论先说

**不用百分比，也不用屏幕像素。** 全工程只有一个坐标系：**1920×1080 设计空间里的 dp**。
由 `StageCanvas` 把「1 设计单位」映射成「N 个物理像素」，N = `min(屏宽/1920, 屏高/1080)`：

| 电视分辨率 | 映射系数 fit | 效果 |
|---|---|---|
| 1920×1080 | 1.0 | 1 设计单位 = 1 物理像素 |
| 2560×1440（2K） | 1.333 | 全部等比 ×1.333，16:9 铺满 |
| 3840×2160（4K） | 2.0 | 全部等比 ×2，**按 4K 原生分辨率重新排版与描字** |
| 21:9 / 4:3 等非 16:9 | 取 min | 等比不变形，四周黑边居中 |

## 2. 为什么不用百分比

百分比只解决"宽度按父容器比例分配"，解决不了这几件事，用了一定翻车：

1. **字号没法用百分比**：`font-size:0.9%` 是相对父元素字号，不是屏幕；结果同一行文字在 4K 上会变得极小或极大。
2. **高度没法用百分比**：`height:8%` 相对父容器高度，父容器没定高就塌成 0。竖排间距、行高全部失控。
3. **圆角/描边/图标线宽没法用百分比**：`border-radius:0.6%` 在宽卡片上变成椭圆角，在窄卡片上几乎没圆角。
4. **比例会被拉伸**：屏幕不是 16:9 时，百分比会填满整屏 → 圆圈变椭圆、字距被拉宽，正是"变形"。
5. **1:1 还原原型就做不到**：原型自己就是固定 1920×1080 + `transform: scale(S)`，百分比等于换了一套布局引擎，所有量过的数值全部作废。

## 3. 专业做法（本工程采用）

```
1920×1080 设计空间（dp = 设计 px）
        │
        ├─ StageCanvas 计算 fit = min(w/1920, h/1080)
        ├─ CompositionLocalProvider(LocalDensity = Density(fit))
        └─ Box(Modifier.requiredSize(1920.dp, 1080.dp))
```

**关键点：不用 `graphicsLayer` 放大。**
`graphicsLayer(scaleX=2f)` 等于先把界面按 1080p 画成一张位图再拉伸，4K 上文字边缘会发虚；
而 `Density(fit)` 是让 Compose **按 2 倍像素重新排版、重新描字**，4K 上是真正的高清。
（早期版本用的是 graphicsLayer，已改掉。）

## 4. 两条硬规矩（写进代码注释）

1. **布局一律用 dp，禁止出现屏幕像素常量**（`Modifier.width(1080f)` 这种写法禁止）。
2. **Canvas / DrawScope 里的数字是物理像素**，必须 `xx.dp.toPx()` 换算。
   焦点环、播放进度条的滑块、圆角、描边都踩过：写死 `3f` 的话，1080p 上是 3px、
   4K 上还是 3px（相对变成 1.5 个设计单位），环会细成发丝、滑块会变小。

## 5. 实测验证

同一份代码、同一台设备，分别在两套分辨率下渲染书架页，然后把我方截图归一化到 1920×1080 做像素差：

| 项 | 数值 |
|---|---|
| 2560×1440 截图（原生） | 2560×1440 |
| 降采样到 1920×1080 后与既有 1080p 截图比对 | **平均差异 MAD = 2.72 / 255（≈1%）**，差异 >8 的像素占 5.81% |

残差来源只有两类，都不是"版式变了"：
- 顶栏 Tab 的焦点环这一轮从"向外扩"改成"向内描"（局部像素差）；
- 字体在 1.333 倍下的栅格化差异（字形边缘 1~2px）。

**结论：1080P / 2K / 4K 三档，几何完全等比，只有"清晰度"在提升。**

## 6. 4K 下还需要注意的（P3 接真实播放时）

- 播放器 Surface 直接给原生分辨率，不要给 1080p 再放大；
- 4K 片源解码要看设备是否有 HEVC/AV1 硬解（`MediaCodec` 能力查询），软解会掉帧；
- 界面层已经是原生渲染，无需额外处理。
